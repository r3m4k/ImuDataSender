# GPIO и светодиоды

Модуль предоставляет шаблонный доступ к отдельным выводам GPIO и управление
светодиодами платы. Исходная платформа — STM32F303; аппаратные вызовы используют
местную STM32F30x Standard Peripheral Library (SPL). `Leds` привязан к BSP
STM32F3 Discovery. Точная маркировка МК, корпус и ревизия платы в рамках анализа
не установлены.

Описание сверено с исходниками 5 ноября 2026 года. Сборка и проверка на оборудовании
не выполнялись. Порядок переноса приведён в [MIGRATION.md](MIGRATION.md).

`GPIO_Pin` не наследуется от других классов и не содержит объектов ресурсов.
`GPIO_Pin_EXTI` публично наследует `GPIO_Pin` и `STM_EXTI::GPIO_EXTI`, а объект
`GPIO_EXTI_n` содержит как закрытое поле. `GPIO_EXTI_n` использует `BaseIRQDevice`
через CRTP. `Leds` — самостоятельный класс; он не использует `GPIO_Pin`.
Динамическая память и пользовательские буферы этим кодом не используются.

## Прикладной интерфейс

Типы GPIO расположены в `STM_CppLib::STM_GPIO`, класс `Leds` — в `STM_CppLib`.
Имена методов и регистр букв являются частью существующего интерфейса.

### Обычный вывод

`GPIO_Pin<GPIO_Port port, uint8_t pin_source>` фиксирует порт и номер вывода
на этапе компиляции. Номер вывода — индекс 0–15, маска GPIO вычисляется отдельно
как `1U << pin_source`.

| Метод | Поведение |
| --- | --- |
| `static constexpr GPIO_Port get_port()` | Возвращает порт |
| `static constexpr uint8_t get_pin_source()` | Возвращает индекс вывода |
| `void InitPin(GPIOMode_TypeDef, GPIOPuPd_TypeDef, GPIOSpeed_TypeDef, GPIOOType_TypeDef)` | Включает тактирование GPIO и заполняет структуру SPL; значения по умолчанию: `GPIO_Mode_OUT`, `GPIO_PuPd_NOPULL`, `GPIO_Speed_50MHz`, `GPIO_OType_PP` |
| `void SetPin()` / `void ResetPin()` | Записывает высокий/низкий уровень в выходную защёлку через SPL |
| `BitAction ReadPin()` | Читает входной уровень через `GPIO_ReadInputDataBit`; результат `Bit_SET` или `Bit_RESET` |

Результат `ReadPin()` относится к входному регистру, а не к последней программной
команде. Физический уровень зависит от режима и внешней схемы, особенно при
Open-Drain. Параметр скорости задаёт характеристику выхода по правилам SPL;
он не обещает частоту переключения 50 МГц.

Пример управления PE9, подключённым в местном BSP к LED3:

```cpp
#include "GpioPin.hpp"

using LedPin = STM_CppLib::STM_GPIO::GPIO_Pin<
    STM_CppLib::STM_GPIO::GPIO_Port::PortE, 9>;

LedPin led_pin;

void init_led_pin(){
    led_pin.InitPin();
    led_pin.ResetPin();
}

void set_led_pin(){
    led_pin.SetPin();
}

BitAction read_led_pin(){
    return led_pin.ReadPin();
}
```

Примеры обычного GPIO и `Leds` используют общие выводы: для одной аппаратной линии
нужно выбрать одного владельца. `InitPin()` не задаёт начальное выходное значение
до переключения режима и не гарантирует отсутствие переходного импульса.

`GPIO_PortDescriptor<port>::get_GPIO_Type()` публично возвращает `GPIO_TypeDef*`,
а `RCC_Periph` — константу тактирования. Дескриптор непосредственно используется
USART. Выбор `GPIO_Mode_AF` сам по себе не настраивает номер альтернативной функции:
это делает вызывающий периферийный модуль через `GPIO_PinAFConfig`.

### Концепт GPIO

`GpioPinConcept` определён в `../Concepts/GpioPinConcept.hpp` и доступен также через
`GpioPin.hpp`. Проверяются выражения вызова методов из таблицы выше и точные типы
их результатов; для `InitPin` проверяется вызов с четырьмя параметрами SPL.
Концепт не проверяет аппаратную совместимость, владение выводом и наличие
инициализации. Требование статичности `get_port()`/`get_pin_source()` самим
концептом не выражено, хотя USART использует эти методы как статические.

### Вывод с EXTI

```cpp
#include "ExtiPin.hpp"

void on_button_irq(){
    // Короткая обработка в IRQ; задержки и блокирующие операции недопустимы.
}

using ButtonPin = STM_CppLib::STM_GPIO::GPIO_Pin_EXTI<
    STM_CppLib::STM_GPIO::GPIO_Port::PortA, 0, on_button_irq>;

ButtonPin button;

bool init_button(){
    // До вызова должна быть подготовлена используемая библиотекой таблица векторов.
    return button.InitPinExti();
}
```

Конструктор не настраивает периферию, но сохраняет указатель на объект регистрации.
Объект следует создавать с временем жизни всей работы IRQ. Копирование и
перемещение запрещены через поле регистрации. Удаление регистрации при разрушении
не реализовано.

`bool InitPinExti(...)` принимает четыре параметра GPIO и затем необязательные
`EXTI_InitTypeDef*` и `NVIC_InitTypeDef*`. Значения GPIO по умолчанию:
`GPIO_Mode_IN`, `GPIO_PuPd_NOPULL`, `GPIO_Speed_50MHz`, `GPIO_OType_PP`.
Без структуры EXTI выбираются прерывание по нарастающему фронту и разрешённая
линия. При первой настройке IRQ без структуры NVIC задаются приоритеты 0/0
и разрешается вектор. Для уже настроенного общего IRQ вызов без структуры
NVIC сохраняет его приоритет и разрешение. Явная структура NVIC перенастраивает
весь общий вектор, включая состояние `DISABLE`, если оно передано.

Путь инициализации из main:

1. Проверить, что явно переданная линия EXTI соответствует выводу.
2. Сохранить `PRIMASK`, запретить маскируемые прерывания, проверить IRQ и
   зарегистрировать статический переходник пользовательского обработчика.
3. При необходимости записать переходник в таблицу векторов и настроить NVIC.
4. Включить тактирование GPIO и настроить вывод.
5. Включить тактирование SYSCFG, очистить pending линии и настроить маршрутизацию/EXTI.
6. Восстановить исходный `PRIMASK`. После этого обработчик уже может быть вызван.

`false` означает несовпадение линии/IRQ либо конфликт регистрации. Эти отказы
обнаруживаются до настройки периферии данным вызовом. Это не универсальная
проверка параметров SPL и не транзакция с откатом при аппаратном сбое.
`true` не гарантирует поступления IRQ при запрещённом NVIC, глобальной маске,
`EXTI_LineCmd = DISABLE` или выборе режима события вместо прерывания.

Из-за публичного наследования доступны также `InitPin()`, `InitExti()` и
`GenerateSWInterrupt()`. Самостоятельный `InitExti()` обходит регистрацию и проверки
`InitPinExti()`; использовать его нужно с пониманием текущего состояния ресурса.
`void SetInterruptPriority(uint8_t, uint8_t)` изменяет приоритет всего IRQ.
Статический `irq_handler()` — переходник к пользовательской функции `void()`.

Аппаратное событие проходит следующий путь:

`IRQ → таблица векторов → BaseIRQDevice → GPIO_EXTI_n → EXTI_IRQ_Dispatcher
→ проверка pending и разрешения линии → очистка pending → пользовательская функция`.

Линии 0, 1, 3, 4 имеют отдельные векторы; линия 2 делит `EXTI2_TS_IRQn` с TSC;
линии 5–9 и 10–15 обслуживаются общими векторами. В каждой группе линии проверяются
по возрастанию номера. TSC подключается отдельно через `RegisterTSCHandler()`;
его обработчик сам проверяет и очищает флаги TSC и вызывается также при событии EXTI2.
Незарегистрированные разрешённые линии этой группы также могут быть очищены
диспетчером. Посторонний обработчик не должен независимо владеть тем же вектором.

В местной SPL `EXTI_Line0…EXTI_Line15` равны индексам 0…15. Передача индекса
в настройку, проверку, очистку и программное инициирование EXTI здесь корректна.

### Светодиоды

| Метод `Leds` | Поведение |
| --- | --- |
| `void Init()` | Инициализирует восемь выводов через BSP; не обнуляет `leds_status` и не задаёт явно состояние On/Off |
| `void LedOn(Led_TypeDef)` / `void LedOff(Led_TypeDef)` | Меняет аппаратуру, затем соответствующий бит локального состояния |
| `void ChangeLedStatus(Led_TypeDef)` | Переключает состояние по локальному биту |
| `void ToggleLed(Led_TypeDef)` | Выполняет `On → Delay(100) → Off`, независимо от исходного состояния |
| `void LedsOn()` / `void LedsOff()` | Последовательно включает/выключает LED3…LED10 |
| `void ToggleLeds()` | Последовательно вызывает `ToggleLed` для LED3, LED4, LED6, LED8, LED10, LED9, LED7, LED5 |

В BSP значения `LED3…LED10` занимают диапазон 0…7, а физические выводы соответствуют
LED4=PE8, LED3=PE9, LED5=PE10, LED7=PE11, LED9=PE12, LED10=PE13, LED8=PE14,
LED6=PE15. Уровень On высокий. Инициализация BSP задаёт выход Push-Pull,
подтяжку вверх и `GPIO_Speed_50MHz`.

```cpp
#include "Leds.hpp"

STM_CppLib::Leds leds;

void init_leds(){
    leds.Init();
    leds.LedsOff();
}

void signal_ready(){
    // Вызывать из main после запуска работающего SysTick с периодом 1 мс.
    leds.ToggleLed(LED3);
}
```

`Delay` реализован в `user/src/main.cpp` через общий счётчик `TimingDelay`.
`SysTick_Handler` в местном `stm32f30x_it.c` вызывает `TimingDelay_Decrement()`.
При периоде SysTick 1 мс один импульс имеет длительность около 100 мс, весь
`ToggleLeds()` блокирует main примерно на 800 мс с учётом работы прерываний.
Точность и верхняя граница времени не гарантированы. Задержка не реентерабельна;
при неработающем или заблокированном SysTick ожидание может не завершиться.

## Владение, время жизни и границы гарантий

| Ресурс | Кто хранит состояние и что требуется от приложения |
| --- | --- |
| Вывод GPIO и тактирование порта | Состояние в аппаратуре; экземпляры `GPIO_Pin` не обеспечивают исключительное владение. Настройку и использование согласует приложение |
| Линия EXTI | Одна общая запись обработчика на номер линии, независимо от порта. Повторная регистрация того же переходника допустима, другого — отвергается |
| Вектор NVIC | Общий приоритет, разрешение и запись таблицы векторов; приоритет и отключение влияют на все источники этого вектора |
| Объект регистрации IRQ | `BaseIRQDevice` хранит статический указатель для специализации. Создание второго объекта того же типа перезаписывает указатель уже в конструкторе; следует использовать один долгоживущий объект |
| Структуры EXTI/NVIC | Используются только во время вызова; указатели не сохраняются. Структуры могут быть локальными, полностью заполненными до вызова |
| Светодиоды | `leds_status` — отдельный байт каждого экземпляра, аппаратные выводы общие. Использовать одного владельца и согласовать обращения main/IRQ |
| Задержка | Общий счётчик приложения и работающий SysTick; параллельные вызовы не поддерживаются |

Обычный GPIO не проверяет `pin_source < 16`; наличие вывода в корпусе и его
электрические параметры также не проверяются. Для EXTI есть проверка диапазона
и ненулевого обработчика на этапе компиляции. Некорректный порт у дескриптора
даёт `nullptr` и константу `0xFFFF`; безопасной обработки такого случая выше нет.

`SetPin`/`ResetPin` в местной SPL записывают отдельные биты через BSRR/BRR.
Это не делает атомарными составные операции, повторную инициализацию или
программное состояние `Leds`. В приложении `Leds` вызывается из main и таймерных
IRQ; обновления одного байта могут теряться даже при работе с разными светодиодами.
Прямые вызовы BSP, включая `Error_Handler`, также обходят локальное состояние.

Инициализацию выполнять из main. Пользовательский EXTI-обработчик работает в IRQ,
без очереди и отложенного вызова; длинные обработчики задерживают другие линии
общего вектора. Флаг pending не является счётчиком событий, дребезг не фильтруется.

Методов `Start`, `Stop`, `DeInit` и снятия регистрации модуль не предоставляет.
Разрушение объекта не отключает EXTI/NVIC, не освобождает линию и не выключает
тактирование. Отключение общего IRQ целиком может остановить соседние линии.

В приложении используется RAM-таблица векторов: `main.cpp` копирует 98 записей,
задаёт выравнивание 512 байт и переключает `SCB->VTOR` перед настройкой устройств.
Это внешнее условие работы `BaseIRQDevice`, а не действие GPIO. Соответствие
таблицы конкретному startup-коду и настройкам линкера требует отдельной проверки.

## Состояние после анализа

Исправлены безусловное разрешение IRQ после восстановления `PRIMASK`, дублирование
`GPIO_Pin_EXTI` и конфликт include guard концепта. Определение EXTI осталось
в `ExtiPin.hpp`, определение концепта — в `Concepts/GpioPinConcept.hpp`.
Описанные ограничения владения, остановки и синхронизации этими исправлениями
не устранялись. Порядок совместного изменения связанных файлов указан
в [инструкции переноса](MIGRATION.md).
