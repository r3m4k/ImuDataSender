# Перенос GPIO на другой микроконтроллер

## Статус и цель

Исходная платформа — STM32F303 и BSP STM32F3 Discovery с местной SPL STM32F30x.
Целевой МК, плата и периферийная библиотека пока не выбраны. Документ описывает
последовательность будущего переноса; аппаратные настройки новой платформы
в нём не назначены. Текущий API и поведение описаны в [README.md](README.md).

Цель — сохранить привычные прикладные вызовы и поведение, заменив аппаратную
реализацию под одну выбранную платформу. Универсальный HAL, переключатели
платформ и одновременная поддержка нескольких МК не требуются. Архитектуру,
структуру модулей, изменение публичных типов и неподдерживаемые возможности
нужно согласовать с Романом до реализации зависящих от них изменений.

Анализ выполнен по исходникам, состояние — 5 ноября 2026 года. Сборка, запуск
и испытания не выполнялись. Перед каждым следующим переносом сверить этот
документ с кодом; он не заменяет документацию выбранного МК и библиотеки.

## 1. Заполнить исходные данные и согласовать решения

| Параметр | Текущее состояние / что определить |
| --- | --- |
| Исходный МК и плата | STM32F303 по исходным данным; BSP STM32F3 Discovery. Точные маркировка, корпус и ревизия не установлены |
| Целевой МК | Не выбран: нужны точная маркировка и корпус |
| Целевая плата | Не выбрана: нужны схема, разводка доступных GPIO и конфликты с периферией |
| Периферийная библиотека | Не выбрана: определить библиотеку и её версию либо согласовать прямую работу с регистрами |
| Выводы приложения | Назначить GPIO и AF; в текущем примере USART1 использует PC4/PC5 |
| EXTI | Определить линии, фронты, маршрутизацию, общие векторы и владельцев совмещённых источников |
| Светодиоды | Определить наличие и соответствие LED3…LED10, физические выводы, активный уровень |
| Задержка | Определить источник тика, единицу времени и допустимость блокирующих импульсов |
| Среда сборки | Подтвердить C++20, пути включения, определения МК и набор исходников библиотеки |
| Доставка IRQ | Проверить startup, доступность переноса таблицы векторов, RAM, выравнивание и настройки линкера |

До чтения дополнительных файлов проекта запрашивать разрешение с объяснением
необходимости. Ранее согласованное чтение зависимостей GPIO/EXTI/IRQ, BSP,
реализации `Delay` и мест использования повторного разрешения не требует.
Файлы сборки и линкерные сценарии в выполненном анализе не изучались.

Публичный интерфейс раскрывает типы SPL: `GPIOMode_TypeDef`, `GPIOPuPd_TypeDef`,
`GPIOSpeed_TypeDef`, `GPIOOType_TypeDef`, `BitAction`, `GPIO_TypeDef`, структуры
EXTI/NVIC и `Led_TypeDef`. Поэтому полная совместимость исходного кода не следует
из одного сохранения имён методов.

После выбора библиотеки согласовать один конкретный вариант: использовать её
родные типы с необходимыми правками мест вызова либо сохранить нужные прикладные
обозначения небольшими локальными определениями совместимости. Сравнить объём
правок и возможность точно передать прежнюю семантику. Не вводить слой
абстракции всех платформ без отдельной договорённости.

Если у новой платы нет восьми светодиодов, а у МК — нужного GPIO, EXTI или режима,
сначала согласовать изменение прикладного контракта или назначений. Молчаливые
заглушки и незаявленные изменения поведения недопустимы.

## 2. Зафиксировать сохраняемое поведение

| Часть API | Что сохранять или явно согласовать при невозможности сохранения |
| --- | --- |
| `GPIO_Port`, `GPIO_Pin<port, pin_source>` | Смысл идентификатора порта и индекса вывода; доступность конкретных портов зависит от цели |
| `get_port()`, `get_pin_source()` | Статические сведения для периферийных шаблонов; проверить точные типы, требуемые концептом |
| `InitPin()` | Порядок параметров: режим, подтяжка, скорость, тип выхода; по умолчанию выход без подтяжки, Push-Pull и соответствующая согласованная характеристика скорости |
| `SetPin()`, `ResetPin()` | Установка/сброс отдельного выхода без изменения соседних битов; без скрытой задержки |
| `ReadPin()` | Чтение фактического входного уровня с прежней семантикой результата |
| `GpioPinConcept` | Один источник определения; соответствие новым типам и реальным потребителям, включая USART |
| `GPIO_Pin_EXTI<port, pin_source, handler>` | Обработчик `void()` без пользовательского контекста; GPIO и методы EXTI доступны через наследование |
| `InitPinExti()` | Результат `bool`, проверки линии/IRQ/конфликта до аппаратной настройки, исходная глобальная маска IRQ сохраняется |
| EXTI по умолчанию | Вход без подтяжки, прерывание по нарастающему фронту, линия разрешена |
| Пользовательские структуры | Синхронное использование без сохранения указателей; явный NVIC `DISABLE` не должен незаметно превращаться в `ENABLE` |
| Общий IRQ | Повторное добавление линии без явной структуры NVIC сохраняет настройку уже используемого вектора; изменение приоритета затрагивает весь вектор |
| Диспетчер | Проверяет разрешённый pending, очищает его перед пользовательским вызовом; сохраняет обслуживание всех совместных источников |
| `GenerateSWInterrupt()` | Программный запрос той же линии через новую аппаратную реализацию |
| `Leds` | `LedOn`/`LedOff`, переключение `ChangeLedStatus`, массовые последовательные операции |
| `ToggleLed()` | Импульс `On → Delay(100) → Off`, а не инверсия; согласовать единицу и точность задержки |
| `ToggleLeds()` | Порядок LED3, LED4, LED6, LED8, LED10, LED9, LED7, LED5 |

Отсутствующие возможности не добавлять как неявную часть переноса: обычный GPIO
не выбирает AF, не фильтрует дребезг и не обеспечивает исключительное владение;
EXTI не имеет снятия регистрации; `Leds` не обеспечивает синхронизацию.
Исправление таких ограничений — отдельное согласованное изменение.

## 3. Изменять связанные части вместе

| Изменение | Файлы и условия, которые нужно проверять совместно |
| --- | --- |
| Порты, адреса, тактирование GPIO | `GpioPort.hpp`, аппаратные вызовы `GpioPin.hpp`, типы в `Concepts/GpioPinConcept.hpp`, потребители `GPIO_PortDescriptor` |
| Типы и режимы GPIO | `GpioPin.hpp`, `GpioPinConcept.hpp`, параметры GPIO в `Exti/ExtiPin.hpp`, места вызова |
| Номер/маска EXTI | `Exti.hpp`: настройка и программный запрос; `ExtiPin.hpp`: проверка линии и очистка pending; `ExtiIRQDispatcher.hpp`: проверка и очистка pending |
| Источник EXTI и его тактирование | `EXTI_Descriptor::PortSource`, маршрутизация в `InitExti`, включение служебного блока в `InitPinExti` |
| Группировка векторов | `EXTI_Descriptor::IRQn`, `vector_index` в `ExtiIRQ.hpp`, битовая карта `initialized_vectors`, `dispatch_irq` и совмещённые источники в диспетчере |
| Число линий и правила владения | Диапазоны шаблонных параметров, таблица `irq_vectors`, проверки регистрации, циклы диспетчера, соответствие линии порту |
| NVIC и доставка IRQ | `Common/BaseIRQDevice.hpp`, EXTI-регистрация, startup и подготовка таблицы векторов в приложении; учесть остальные модули на том же базовом классе |
| Альтернативные функции USART | `UsartTxChannel.hpp`, `UsartRxChannel.hpp`, соответствия выводов/AF и аппаратные вызовы USART; актуальные таблицы проверять по выбранному МК |
| Светодиоды | `Leds.hpp`, BSP `stm32f3_discovery.h/.c` или согласованная замена, `Led_TypeDef`, полярность, маска состояния и прямые вызовы BSP приложением |
| Время импульса | `Leds.hpp`, объявления в `main.h`, `Delay`/`TimingDelay_Decrement` в `main.cpp`, настройка и фактический обработчик SysTick |
| Заголовки | Единственное определение концепта в `Concepts/GpioPinConcept.hpp`, единственное определение EXTI-пина в `Exti/ExtiPin.hpp`; согласовать пути включения |

Здесь перечислены связанные изменения, а не требование переписать все эти файлы:
менять следует только то, что нужно для выбранной цели и согласованного API.

## 4. Перенести обычный GPIO

1. Сопоставить доступные порты, выводы корпуса и константы тактирования. Не считать
   наличие регистра доказательством наличия вывода на плате.
2. Заменить включение тактирования в `InitPin`. Проверить требуемую задержку
   или барьер после включения по документации целевой платформы.
3. Перенести режимы, подтяжки, тип выхода и характеристику скорости. Обозначение
   `GPIO_Speed_50MHz` не переносить механически как частоту работы приложения.
4. Настроить запись одного бита без чтения и обратной записи всего выходного
   регистра, если аппаратура предоставляет отдельные set/reset-регистры.
   Если прежние свойства нельзя сохранить напрямую, согласовать решение.
5. Сохранить чтение входного регистра. Проверить Open-Drain, аналоговый режим,
   начальное состояние и влияние внешней нагрузки.
6. Отдельно перенести AF в потребителях GPIO. Текущее приложение использует
   `GPIO_Mode_AF` и затем `GPIO_PinAFConfig` в компонентах USART.

Текущий `InitPin` не предзагружает выходное значение и не гарантирует отсутствие
импульса при смене режима. Если новая схема требует безымпульсного включения,
обсудить начальный уровень и порядок операций до изменения API или реализации.

## 5. Перенести EXTI и доставку IRQ

1. Установить формат аргумента линии в новой библиотеке. В исходной местной SPL
   `EXTI_Line0…15` — индексы 0…15, и вызовы с `pin_source` корректны. Если новая
   библиотека принимает маску, преобразование требуется во всех точках из таблицы
   связанных изменений. Индекс вывода GPIO и номер/маску EXTI не смешивать.
2. Сопоставить порт, номер вывода, аппаратную линию и IRQ. Текущая схема с одной
   линией на индекс вывода и общими группами 5–9/10–15 относится к исходному МК.
3. Пересчитать индексы групп и размеры хранилищ. Сейчас есть 16 обработчиков
   и семь битов в `uint8_t initialized_vectors`; эти числа не универсальны.
4. Согласовать все источники общего IRQ. Исходный `EXTI2_TS_IRQn` требует
   обслуживания EXTI2 и отдельно зарегистрированного TSC. Другие совмещённые
   источники новой платформы нельзя оставлять с неочищенным флагом.
5. Проверить доступность RAM-таблицы векторов и способ её активации. Сейчас
   `BaseIRQDevice` пишет `_user_vector_table[16 + IRQn]`, а `main.cpp` копирует
   98 записей и устанавливает `SCB->VTOR` с выравниванием 512 байт. Размер,
   выравнивание, размещение и сам способ доставки IRQ определить заново.
   Если прежний механизм недоступен, согласовать замену до реализации.
6. Сохранить критическую секцию и восстановление исходной маски IRQ на всех
   путях выхода. Безусловный `__enable_irq()` после восстановления недопустим.
   Не менять глобальную группировку приоритетов NVIC скрыто внутри GPIO.
7. Сохранить порядок: проверка параметров/конфликта → регистрация → настройка
   NVIC под глобальной маской → GPIO → служебный блок и EXTI → восстановление
   маски. Если аппаратуре нужен иной порядок, проверить отсутствие окна вызова
   неполностью настроенного обработчика и согласовать изменение.
8. Перенести проверку pending и очистку перед callback по правилам аппаратуры,
   включая семантику записи единицы для очистки. Не очищать соседние источники
   общей маской без необходимости.
9. Сохранить правила повторной регистрации и общих приоритетов. Не менять
   занятый обработчик молча. `true` от инициализации не трактовать как гарантию
   фактического разрешения всех аппаратных и глобальных масок.

Указатели на пользовательские структуры EXTI/NVIC не должны переживать вызов
внутри библиотеки. Объект IRQ, напротив, должен оставаться живым всё время
обслуживания. В исходной архитектуре нет снятия регистрации; временные объекты
и их разрушение не образуют поддерживаемого сценария остановки.

## 6. Перенести светодиоды и задержку

Составить таблицу «логический LED → вывод платы → активный уровень». Текущие
LED3…LED10 имеют значения 0…7, помещаются в один байт `leds_status` и используют
PE8…PE15. При другом перечислении нельзя сохранять сдвиг в байте без проверки
диапазона. При другой полярности логический `LedOn` должен по-прежнему включать
светодиод, даже если физически требуется низкий уровень.

Согласовать замену BSP в рамках одной целевой платы. Учесть, что `Leds::Init`
только настраивает выводы, не обнуляет локальное состояние и не задаёт On/Off;
примеры явно вызывают `LedsOff` для начального состояния. Прямые вызовы BSP
в приложении могут рассинхронизировать этот байт.

Проверить источник `Delay(100)`. В текущем приложении это общий счётчик,
уменьшаемый SysTick с периодом 1 мс. Сохранить блокирующий импульс около 100 мс
либо предварительно согласовать изменение. Не превращать `ToggleLed` в обычную
инверсию и не объявлять задержку пригодной для IRQ без проверки выполнения тика.

## 7. Разделять дефекты, ограничения и требования переноса

| Категория | Установленные факты и действия |
| --- | --- |
| Исправленный дефект исходника | Лишний `__enable_irq()` после восстановления `PRIMASK` удалён; единственная реализация теперь в `ExtiPin.hpp` |
| Исправленные дефекты заголовков | Дубликат `GPIO_Pin_EXTI` удалён из `GpioPin.hpp`; у концепта отдельный include guard и одно определение в `Concepts/GpioPinConcept.hpp` |
| Корректное поведение исходной SPL | Индекс линии EXTI не является ошибкой; это подтверждено местными `stm32f30x_exti.h/.c` |
| Ограничения архитектуры | Нет владения обычным GPIO и снятия регистрации EXTI; несколько экземпляров одного EXTI-типа перезаписывают статический указатель на объект |
| Ограничения `Leds` | Локальный несинхронизированный байт состояния, возможные потерянные обновления main/IRQ и рассинхронизация при прямом доступе BSP; `Delay` не реентерабелен |
| Необходимые изменения переноса | Адреса, тактирование, режимы, представление EXTI, маршрутизация/IRQ, AF, BSP, полярность и источник времени — по выбранной платформе |
| Требует дополнительной проверки | Точная плата/корпус, доступность выводов, startup/линкер, реальный состав сборки, временные характеристики, отсутствие импульсов при переключении |

Обычный GPIO пока не проверяет диапазон номера вывода, а доступность порта
и выводов корпуса не проверяется ни им, ни концептом. Не считать исходную
реализацию проверенной на оборудовании и не переносить её ограничения как
обязательные свойства нового МК. Дополнительные исправления обсуждать отдельно.

## 8. План проверки после отдельного разрешения на запуск

Ниже перечислены предлагаемые проверки; наличие этого списка не разрешает
сборку, тесты, запуск проекта или прошивку без отдельного указания Романа.

- Проверить сборкой C++20 самостоятельное и совместное включение `GpioPin.hpp`,
  `GpioPinConcept.hpp`, `ExtiPin.hpp` в обоих порядках; отсутствие переопределений.
- Проверить соответствие обычного GPIO концепту и сборку потребителей USART.
  После выбора библиотеки проверить явные аргументы GPIO/EXTI/NVIC и умолчания.
- На оборудовании проверить режимы входа/выхода, подтяжки, Push-Pull/Open-Drain,
  чтение входа, сохранение соседних битов и выбранные AF.
- Проверить сохранение маски IRQ после успешной и неуспешной инициализации
  при первоначально разрешённых и запрещённых прерываниях.
- Проверить неправильную линию/IRQ и конфликт двух портов на одной линии:
  отказ до изменения аппаратных настроек; повторная регистрация того же
  переходника должна сохранять предусмотренную семантику.
- Проверить аппаратный и программный EXTI, фронты, очистку pending до callback,
  одновременные линии общего IRQ и его приоритеты. Для нового источника,
  поступившего во время обработки, проверить поведение по документации МК.
- Проверить общий IRQ с источниками вне GPIO, а также сохранение явного
  `DISABLE` и настроек уже используемого вектора.
- Проверить LED On/Off, `ChangeLedStatus`, порядок `ToggleLeds`, полярность
  и длительность импульса при выбранном тике. Проверить внешние вызовы BSP
  и сценарии main/IRQ, если они остаются в приложении.
- Проверить таблицу векторов в итоговой прошивке: размер, адрес, выравнивание,
  соответствие IRQ, действующую маршрутизацию и отсутствие перезаписи
  регистраций последующим копированием исходной таблицы.

Перенос считать завершённым после согласования всех изменений контракта,
проверки связанных потребителей и фиксации реально выполненных проверок
с их результатами. Обновить оба документа под конкретный МК и плату;
не отмечать непроведённые испытания как успешные.
